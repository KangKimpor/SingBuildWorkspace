## D-32 Editing and snapshot performance at BOQ scale - November 12, 2026

The live workspace holds 17,472 NBC activities (16,550 in BP02, about 11 MB of jsonb). Three per-edit costs grew with that and made the app feel laggy. (1) The sync subscriber diffed every row of a changed collection with two `JSON.stringify` calls, and `contentOf()` rebuilds the submission and summary arrays on every call, so every edit (a page keystroke included) also re-serialised all submissions. Store updates replace only the rows they change, so `queueChanges` and `persist` now treat an identical row object as unchanged and serialise only rows that are new objects; a rebuilt row with the same content is still compared by JSON and not queued (test in `egress-optimization.test.ts`). Measured on synthetic data of the same shape: 89 ms → 5 ms for an activity edit, 9.6 ms → 0.1 ms for the submissions pass. (2) The debounced IndexedDB snapshot ran `structuredClone` on the whole workspace (≈130 ms) before IndexedDB cloned it again. The explicit clone is dropped (nothing mutates store rows in place; `transitionSubmission` clones its input first) and the write waits for `requestIdleCallback` (2 s timeout). The `pagehide`/`visibilitychange` flush is unchanged. (3) The Update Progress editor re-ran `draftEntries` over every activity and a full `calculate` for the previous-week column on each keystroke; both are memoized on the store slices and entries they read. Its table stays non-virtual (033d368). Also: page-wide NBC styling keys off `html[data-nbc]`, set by `NbcProject` in a layout effect, instead of `html:has(.nbc-project)` (same specificity; avoids document-wide `:has` invalidation, notably in Safari). Lazy route chunks are prefetched one per idle callback after first paint in production builds, skipped when Save-Data is on. The page editor and XLSX export still load on demand. None of this changes a Supabase request: no query, realtime channel or write was added, removed or resized.

## D-34 BP02 room matrix on iPad: render one row per edit, roll up one floor - November 13, 2026

BP02 still felt slow on iPad after D-32. Live BP02 (aggregate query, no rows downloaded) has 11 floors, each showing 116 matrix rows (80 tasks) across 14–23 room columns, so a floor holds about 2,000 cells; Tola alone has about 9,900 cells. `corepack pnpm perf:bp02` (`e2e/perf`, `playwright.perf.config.ts`) seeds a synthetic BP02 of the same shape (`bp02-fixture.ts`, 16,845 activities) straight into IndexedDB, because WebKit's localStorage cannot hold it, and times each interaction inside the page at iPad size. It reports both the first frame after the input and the moment the result is on screen. Chromium runs at 4× CPU throttle as an iPad proxy; results go to `perf-results/` (git-ignored). Medians, 4× Chromium, before → after: Update keystroke 155 → 63 ms, Update collapse group 275 → 96 ms, Overview → Project Progress 563 → 129 ms, Update → Project Progress 712 → 409 ms. First frame after a floor tap: Update 569 → 50 ms, Project Progress 482 → 48 ms. Desktop WebKit was already fast; its taps now paint in about 40–50 ms (from 60–140).

What changed: (1) Every keystroke looked up each of ~950 cell values with a linear `rows.find` over Tola's ~10,000 entries, re-parsed all of them and re-ran `calculate` over all 16,550 activities. `useUpdateDraft` now keys entries by id, parses an untouched row once per `rows` and memoizes on the form values; the editor rolls up only the floor it shows (a floor's figures depend only on its subtree). (2) `RoomMatrix` renders rows through a memoized `MatrixRow` that a caller opts into with `rowSignature` (everything a row's cells show beyond the row object and its Prev/Now values). A keystroke now re-renders one row instead of ~2,000 cells. Without the keep-alive the Free Plan project can pause after seven days with no requests, for example over a long holiday; restoring it is one click in the dashboard.

**Egress.**
- *Realtime sent full rows.* Every write echoed its whole row to every subscriber, the writer included (a page save sent the page back, a Confirm sent submission rows averaging 145 KB), and the 12 Nov BP02 migration sent one message per row for 16,099 rows. Statement-level triggers (`kw_private.broadcast_changes()`, `20261115073911`) now broadcast `{collection, rows:[{id, updated_at}]}` once per statement, or `{collection, refresh:true}` above 200 rows, on the private topics `kw-workspace:<uid>` and `kw-nbc:<project>` (staff-only policy `kw_nbc_receive`). Clients queue the ids for 150 ms and fetch only rows newer than the version they render, in one request and one store update per collection, so a writer never downloads its own write (`receiveChangeNotice` in `src/data/sync.ts`, `NbcProject`).
- *Watermarks.* Acknowledged own writes no longer advance a delta watermark, because a row another session is still committing can be older than that ack and would be skipped. Delta pulls re-read the last 10 s; for the manifest collections that costs only `id,updated_at`. A write queued while `refreshCollections` holds the queue is now pushed when it finishes.
- *Frozen weeks.* Confirmed submissions store every assigned activity (47,364 entries, 7.8 MB in 55 rows) and every new device downloads all weeks. `kw_private.nbc_compact_frozen_submissions()` drops no-op entries (progress equal to previous, remark unchanged) from confirmed weeks older than last week. A rolled-back dry run took submissions from 7.8 MB to 2.7 MB.
- *Recovered pages.* 41 "Recovered edit" pages, JSON dumps of rejected BP02 drafts, were 8.06 of the 8.07 MB in `kw_pages`. They were moved to `kw_private.recovered_pages_archive` and removed from `kw_pages`, which is now 4.6 KB. `recoverConflict` now keeps only changed submission entries.

The publication drop and the weekly compaction job (Sunday 00:30 Phnom Penh) are in `20261115082848_post_deploy_drop_postgres_changes.sql`, which ran once this client was live in production (b79b4f6): older clients subscribe to `postgres_changes` and compute Needs review from full coverage. After it ran, the publication is empty and submissions are 2.7 MB (38 frozen rows compacted, 4 marked Needs review). The id broadcasts are additive and already live. Dropping the publication also stops the Realtime WAL polling query, the project's largest consumer of database time (1.35 million calls).

**Client performance.**
- *Per-row snapshot.* A signed-in workspace was one IndexedDB record (about 26 MB for BP02) rewritten 1.2 s after every change and on every tab hide. Dexie version 3 adds `rows` (`[scope+collection+id]`) and `meta`. `persistSnapshot` compares row objects by identity against what it last wrote, writes only changed rows, deletes removed ones, converts the old record once and replaces the whole snapshot after a failed write. Snapshot failures never fail a sync. The guest workspace keeps its single record.
- *Service worker.* The update check timer runs every 30 minutes instead of every minute, since focus, visibility and reconnects already check. Excluding the page editor and emoji chunks from the precache was tried and reverted: a page opened before the worker took control was never cached, so `workspace.spec.ts` "page editing survive a reload offline" failed, and the saving was about 1 MB of Vercel download per install with no Supabase egress. Not changed: `nbc_submission_write` still averages about 1.3 s on BP02, because Confirm adds an unchanged entry for every assigned activity in the editable window. Compaction does not reach that window. The BP02 Weekly 63 backups in `kw_private` (14 MB) are kept until the owner says they are no longer needed; they cost no egress unless exported. Leaked-password protection is a Pro Plan feature.

## D-48 Sync watermark ordering, restore-flush guard, and NBC calculation self-healing - November 21, 2026

A signed-in browser could end up with a partial `nbc_activities` IndexedDB snapshot (for example, holding only the two non-editable rows touched by `20261121065500` for BP03/BP04 while BP02 stayed intact), leaving the sidebar at `0%` and `NbcProject` permanently paused on `"Calculation needs attention. Progress editing is paused."` even though Supabase was intact (`✓ Saved to cloud`).

1. **Advance watermarks only after rows apply (`src/data/sync.ts`).** `pullCloud()` previously updated `watermarks` *before* the batched `toFetch` requests finished and before `applyRemotePatch()` committed rows to the store, so a mid-batch network failure or `pagehide`/`visibilitychange` flush could persist a watermark ahead of the stored rows and permanently skip them. Watermarks now advance only after all batches succeed and `applyRemotePatch()` commits.
2. **Guard snapshot and recovery writes during startup restore (`src/data/sync.ts`).** `writeChangedRows()` and `saveRecovery()` now bail out while `restoring` is in flight so a `pagehide`/`visibilitychange` event during `readSnapshot()` cannot flush `emptyContent` over `db.rows` or delete the localStorage recovery journal. `flushNotices()` also defers to `syncWorkspace()` until `hydrated` is true.
3. **One-time manifest reconcile (`src/data/sync.ts`).** Bumped `RECONCILE_AFTER` to `2026-11-21T07:00:00Z` so existing devices run one low-egress manifest reconcile (pruning the 25 rows deleted from BP04 by `20261119083231` and restoring any missing BP03/BP04 rows without re-downloading unchanged BP02 rows). `syncWorkspace(refresh, full)` now accepts `full = true`, wired to Settings → **Retry / reconnect** (`src/components/AccountSettings.tsx`).
4. **Automatic and manual recovery on calculation failure (`src/nbc/NbcProject.tsx`).** When a signed-in project has activities that fail `calculate()` after sync settles, `NbcProject` automatically runs one project-scoped manifest reconcile (`refreshCollections(['nbc_activities'], { full: true, projectId })`) and exposes a **Reload from cloud** button on the warning banner.
5. **Prevent `activeRun` lockup on synchronous no-op syncs (`src/data/sync.ts`).** `syncWorkspace()`, `refreshCollections()`, and `flushNotices()` previously assigned `activeRun = (async () => { ... finally { activeRun = undefined } })()`; when a no-op call completed without hitting an `await`, `finally` cleared `activeRun` *before* the outer assignment ran, permanently pinning `activeRun` to a resolved promise and blocking subsequent syncs. Guarding the assignment with a `finished` flag eliminates this deadlock.

## D-70 Always load the latest version on open/refresh and block outdated loads - November 26, 2026

1. **Build version manifest.** `vite.config.ts` generates a unique `__APP_VERSION__` per build and emits `dist/version.json` (`{ "version": ... }`), also served in dev.
2. **Never serve cached HTML.** `vercel.json` sets `Cache-Control: no-cache, no-store, must-revalidate` on the catch-all `/(.*)` (overridden to immutable only for content-hashed `/assets/(.*)`) and explicitly on `/index.html`, `/sw.js`, and `/version.json`, so every SPA route (`/`, `/admin`, `/projects/...`) fetches fresh HTML. Workbox drops `html` and `version.json` from precaching (`navigateFallback: null`), keeps `clientsClaim: true`, and stops intercepting navigations with stale precached `index.html`.
3. **Strict startup version gate.** Before `src/main.tsx` initializes workspace data or mounts `<App />`, `enforceLatestVersion()` (`src/lib/versionGate.ts`) fetches `/version.json?_t=...` with `cache: 'no-store'` and compares it to `__APP_VERSION__`.
   - If the version is outdated, it unregisters stale service workers, clears Cache Storage, and reloads immediately without mounting the old app (capped at 2 automatic reloads per 30 s target; if still mismatched, it renders a blocking **Update required** screen with a manual **Reload latest version** action).
   - If `/version.json` cannot be reached or verified, it refuses to mount the app and renders a blocking **Latest version required** screen with **Try again**.
   - Restoring a page from browser back-forward cache (`pageshow` with `event.persisted`) re-runs the same gate, and `registerUpdates()` checks `/version.json` alongside `registration.update()` on `focus`, `online`, `visibilitychange`, and every 5 minutes so open tabs adopt new deployments promptly.
